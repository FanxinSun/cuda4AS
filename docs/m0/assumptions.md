# M0 assumption register

This register prevents a local observation, an upstream claim, or a proposed
mechanism from becoming an implementation guarantee without the test that
would justify it.

Statuses used here are `SPEC_CONFLICT`, `OBSERVED_LIMITED`,
`UPSTREAM_REPORTED`, `PROPOSED_UNVALIDATED`, and `UNRESOLVED`. They describe
evidence, not the result classifications in
[`compatibility.md`](compatibility.md).

## Register

| ID | Status | Assumption and evidence | Bounded M0 conclusion | Test or decision needed to close it |
| --- | --- | --- | --- | --- |
| A-01 | `SPEC_CONFLICT` | Returned p3 A1/A2 values were produced by `simdgroup_barrier` calls in divergent branches. The [Metal Shading Language Specification 4.1](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf), dated 2026-06-04, pp. 215–216, requires every thread in the SIMD group to enter a conditional and execute the barrier when any thread does. | The zero-mismatch A1 observation is behavior from a pattern that does not satisfy the documented participation precondition. It cannot be promoted to portable synchronization or decoder safety. | Replace positive conformance cases with uniform-participation barriers; add negative diagnostics for divergent barriers; test across supported OS/GPU configurations. Audit each decoder barrier independently. |
| A-02 | `UNRESOLVED` | The copied lmz prefetch shader contains barriers under conditions whose values can vary by lane. p8 never reached GPU execution because the unmodified host harness obtained no default device. | Neither p3 nor p8 establishes that the prefetch decoder is correct on an Apple GPU. The direct path and prefetch path remain separate candidates. | Use a cuda4AS-owned host harness with the unchanged pinned shader and data; prove barrier participation for each path; require byte-identical direct and prefetch outputs and GPU provenance. Do not edit lmz. |
| A-03 | `OBSERVED_LIMITED` | p2 measured bounded global-atomic arrival behavior for nine threadgroup-size/memory configurations on one M1 Pro. The curve is nonmonotonic and the probe has a fixed spin cap. | A measured co-resident count is an experiment under those conditions. It does not prove arbitrary-kernel forward progress, a portable scheduler contract, or general `grid.sync()` safety. | Test a correctness-preserving grid-barrier mechanism, preferably eligible kernel splitting with live-state checks. Add adversarial occupancy, side-effect, loop, divergence, and multi-OS/device cases. Reject or explicitly fall back when proof conditions fail. |
| A-04 | `OBSERVED_LIMITED` | `vm_remap` and `mach_vm_remap` at one Metal GPU address both returned `KERN_NO_SPACE` on the recorded M1 Pro. `bytesNoCopy` was coherent, while CPU and GPU addresses differed. | Those two fixed-address attempts failed. They do not prove that every managed-memory strategy, address representation, reservation order, or supported sparse mechanism is impossible. | Test ordinary multi-buffer pointer semantics first. Evaluate safe reservation/address-translation alternatives in isolated experiments and across OS/device versions. Any overwrite experiment requires its own risk review; M0 performs none. |
| A-05 | `OBSERVED_LIMITED` | p1 reached `MTLDevice.maxBufferLength` at 8 GiB in shared and private storage without touching the pages. The recorded recommended working set is 10.67 GiB. Apple's [`maxBufferLength`](https://developer.apple.com/documentation/metal/mtldevice/maxbufferlength) property describes the maximum length of one buffer. | Maximum single-buffer length, virtual allocation success, aggregate allocatable bytes, committed backing, and safe working capacity are different quantities. The run establishes only the first under its allocation conditions. | Exercise multiple allocations, touch/readback, aliasing, lifetime, memory pressure, out-of-memory behavior, and `currentAllocatedSize`; report individual, aggregate committed, available, and configured virtual capacities separately. |
| A-06 | `SPEC_CONFLICT` | The old macOS 14.4/Xcode 15 probe reports `metal4` false and cannot compile MSL 4. Apple's [Metal feature tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf), dated 2026-05-21, list M1-series/Apple7 under both Metal 3 and Metal 4 programming models. | An old OS/SDK/API result is not a permanent GPU-family limitation. Programming model, language/compiler, OS, SDK, GPU family, and individual features require separate fields. | Run the same capability manifest on the baseline and a newer supported OS/SDK without overwriting either result. Query individual device properties and compile/load the required operation before claiming it. |
| A-07 | `UNRESOLVED` | The historical blueprint says Metal lacks sparse buffers. Apple's current feature tables list placement sparse buffers under Metal 4 and state that some Apple7 macOS devices, and all Apple8 devices, support placement sparse resources through a runtime capability check. The existing probes do not query that property. | Current sparse-buffer support on the recorded M1 Pro configuration is unknown. Sparse placement would still not establish CUDA demand paging, page-fault recovery, pointer identity, automatic oversubscription, or sufficient active working-set capacity. | Add a bounded capability/allocation/map/unmap/coherency probe on each target configuration; then test the separate CUDA residency contract and failure modes. |
| A-08 | `OBSERVED_LIMITED` | p7's Xcode 15 compiler rejected tested `atomic_ulong` load/add/min/CAS forms on Apple7 and accepted uint and float-add controls. Apple's feature tables describe only min/max on some Apple8 macOS devices and the full 64-bit atomic set from Apple9. | “Apple supports” and “Apple lacks” are both too broad. Native operations must be selected per OS/SDK/device/operation/order/scope. A lock-backed implementation is only a proposal and can deadlock without proven progress. | Build an operation × type × address-space × ordering × scope matrix. Test native selection, contention, forward progress, wraparound, compare-exchange, and memory visibility. Keep emulated results distinguishable. |
| A-09 | `PROPOSED_UNVALIDATED` | The Metal compiler rejected `double`; the inherited `double_dot` fixture is exact by construction and its own source notes that a reduced ~48-bit representation can reproduce that narrow case. | Passing `double_dot` cannot establish faithful CUDA binary64. The default target remains faithful binary64 for the declared operation set; reduced precision and CPU execution are explicit modes. | Add rounding, cancellation, subnormal, signed-zero, NaN/infinity, conversion, comparison, aliasing, atomic, and math-function tests against independent binary64 references. Publish separate results for every numerical mode. |
| A-10 | `UNRESOLVED` | Linux has portable build tools and CUDA oracle access; the returned Mac compiled Swift probes. Neither fact demonstrates cuda4AS native host compilation, Objective-C++/Metal framework linking, AOT metallib packaging, install discovery, or execution. LLVM's [CUDA documentation](https://llvm.org/docs/CompileCudaWithLLVM.html) says its normal CUDA compilation path is no longer supported on macOS. | A clang executable is one prerequisite, not the complete G-C1 dependency. A Linux compiler-only success cannot be an end-to-end result. | In M1, pin a candidate, configure and build it on a declared Mac, compile an unchanged CUDA source, link native arm64 host/runtime/framework code, execute on GPU, and validate install/runtime discovery. |
| A-11 | `UPSTREAM_REPORTED` | CuMetal main resolved to candidate commit [`f486e5ebcfd381d06e3297afd65dbcbd5006a902`](https://github.com/Lulzx/cuda-metal/commit/f486e5ebcfd381d06e3297afd65dbcbd5006a902) during M0. Its [verified-results record](https://github.com/Lulzx/cuda-metal/blob/f486e5ebcfd381d06e3297afd65dbcbd5006a902/docs/verified-results.md) reports unchanged cuda-samples and llama.cpp build/execution slices, with stated limitations. | These are useful upstream claims and make CuMetal the first reuse candidate. They are not cuda4AS validation or an adoption decision. Main is moving and must not be treated as a reproducible revision without a pin. | M1 must pin a reviewed revision and license, reproduce the smallest Apple-GPU source path, run selected cuda4AS corpus cases, inspect source/build diffs and execution evidence, and issue adopt/selective-reuse/build decisions for manager review. |
| A-12 | `OBSERVED_LIMITED` | p0/p3 report a SIMD width of 32, and the ballot-prefix fixture matched on one Apple7 configuration. | Width equality does not make every CUDA warp intrinsic, mask, width, partial-warp, divergence, or memory-order behavior identical. | Test active masks, partial warps, shuffle widths/modes, vote operations, warp synchronization, divergent control flow, and source diagnostics over varied block sizes. |
| A-13 | `PROPOSED_UNVALIDATED` | The recorded device exposes 32,768 B threadgroup memory while `shared_48kb.cu` requests 49,152 B. The blueprint proposes spilling excess shared storage to device memory. | The native capacity mismatch is observed; correctness of the proposed spill transform is not. Device-backed storage changes addressing, fencing, allocation, and failure behavior. | Run the unchanged 48 KiB oracle plus boundary/alignment/isolation/dynamic-shared/shared-atomic cases; prove barriers fence the actual storage and test allocation/resource-accounting failures. |
| A-14 | `OBSERVED_LIMITED` | `MTLCreateSystemDefaultDevice()` returned nil in the recorded Aqua Terminal session while `MTLCopyAllDevices().first` returned the M1 Pro. | The runtime must not rely only on the default call. One result does not explain the cause or guarantee that the fallback is universally correct when several devices exist. | Define deterministic selection and error rules; test zero/one/multiple devices, headless sessions, overrides, permissions, and device loss across the supported matrix. |
| A-15 | `OBSERVED_LIMITED` | Run 1 produced ten valid “no Metal device” JSON documents and exit code zero, while `status.txt` labeled all ten `ok`. Run 2 uses `ok` even when a capability such as p6 tensor execution is absent. | File existence, process success, and probe completion are not compatibility passes. Historical schema 1 is evidence input only. | Validate required fields, backend, stages, assertions, and aggregate status against the new result contract. Add a regression fixture based on run 1's false-positive shape. |
| A-16 | `PROPOSED_UNVALIDATED` | The initial profile proposes `__CUDA_ARCH__=860` to select an Ampere-oriented source path. No dispatch corpus has exercised that choice through cuda4AS. | The macro is a profile hypothesis, not evidence for all Ampere operations or a license to ignore requested architecture flags. | Compile preprocessor/constexpr dispatch fixtures and pinned application paths under representative `-arch`/`-gencode` inputs; require supported selection or a useful diagnostic for mandatory unavailable features. |
| A-17 | `PROPOSED_UNVALIDATED` | The blueprint proposes compiling device IR for arm64 as a CPU fallback and debugger. CUDA barriers, warps, shared memory, atomics, and error/ordering behavior do not follow automatically from ordinary CPU code generation. | CPU mode is a separate execution model and cannot hide a GPU gap. It may only be reported when explicitly selected. | Specify and test thread/block scheduling, synchronization, atomics, memory, errors, source locations, and determinism; classify successful runs as `PASS_CPU_EXPLICIT`. |
| A-18 | `OBSERVED_LIMITED` | p4/p5 use short best-of-five GPU intervals and calibrated loops on one M1 Pro. The historical report already labels peak figures as lower bounds and ratios as more trustworthy. | These values are useful probe observations, not sustained rates, cross-device expectations, or cuda4AS performance. | For future performance claims record first-use/warm distributions, median/tail, dispatch and copy costs, power/thermal conditions, algorithms, precision, dimensions, and same-device native comparators after functional conformance. |

## M0 decisions carried into later work

- Compatibility and correctness remain first; performance cannot convert a
  failed or unsupported semantic case into a pass.
- The existing M1 Pro remains a baseline configuration, not the target
  envelope. Every result carries machine, OS, SDK/compiler, and conditions.
- GPU behavior is the default goal. CPU and reduced-precision paths are useful
  only when explicit and separately classified.
- CuMetal is the first candidate to evaluate in M1. M0 makes no compiler/runtime
  adoption decision.
- Historical evidence stays immutable. Corrected interpretations live in this
  register and in [`baseline.md`](baseline.md).
