## Objective and entry

Move beyond regular toy kernels using bounded, representative scientific and
irregular extracts, while treating concurrency/precision requirements as hard
contracts. Require the specific compiler/runtime/library prerequisites of each
case, not merely a milestone number. Preserve all earlier negative evidence.

The static survey identifies candidates from Awkward, ROOT/TMVA, VecGeom, ACTS,
Celeritas and related work; it is not a license/provenance audit or proof those
complete applications can run. Sibling trees are read-only unless separately
authorized. Enroll extracts before full applications.

FP64/VF64 remains held by default. Selecting emulation would require a separate
architecture, licensing, performance/resource and user-value decision. Do not
substitute FP32 or adjusted input data. OptiX, texture/ray-tracing, tensor-specific
instructions and cooperative mechanisms not covered here remain R-NVIDIA
replacement/unsupported decisions; none are implied by the frontier table.

## Result contracts

Scientific cases name conserved quantities, residuals, physical bounds, acceptable
bias/drift and domain-relevant observables, not just maximum element error.
Geometry cases include boundaries, degeneracy, units and classification stability.
RNG contracts distinguish bitwise sequence reproducibility from statistical
equivalence; fix generator, seed, stream and sample-size/confidence method.

Concurrency cases specify participation, ordering, memory scope and progress.
Use schedule/shape variation and collision-heavy inputs without relying on
undefined source behavior. Timeouts and intermittent failures remain failures
or explicit incomplete evidence, never an averaged pass.

CPU/specification/NVIDIA triangulation is diagnostic: document implementations,
precision and known algorithmic differences. Three agreeing outputs are stronger
evidence only if they are meaningfully independent. A disputed reference blocks
the associated claim until explained. Golden data is never regenerated using
the candidate under test.

## Cross-target evidence and resources

Start with the actual M1 Pro; record unavailable targets as NOT_RUN. The target
matrix distinguishes hardware features from OS/SDK API availability. A newer
SDK compiling an API does not prove the older hardware implements it, and a
missing API on the recorded SDK does not establish universal hardware absence.

Per case freeze maximum data size, threads/groups, repetitions, wall time and
memory/storage envelope. Use smaller diagnostic extracts before realistic
scale, but do not promote a tiny extract to full-application performance.
No new machine, remote GPU, download or compiler installation is implied.
