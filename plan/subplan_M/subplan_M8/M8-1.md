# M8-1 — Workload enrollment, route choice and practical value

Parent step: M8-1 in [M8](../M8.md).
State: PLANNED_NOT_AUTHORIZED. No survey candidate is selected for execution yet.

## Objective

Choose a finite, reproducible recurring job whose offload could release useful
RTX 5080 time while fitting the actual M1 Pro and the user's deadlines. Make
technical compatibility, scientific/ML correctness and practical value separate
verdicts. A slower Mac result can be useful; a faster kernel with excessive
setup/recovery cost can be useless.

## Required workload record

Identity: repository/application version, task, input subset/hash, model/weights
and preprocessing where applicable, expected outputs and allowed source changes.
Workload value: frequency, current RTX5080 hours per run/week, queue pressure,
deadline, maximum acceptable Mac wall time and required latency/throughput.
Resources: peak host/device memory, per-buffer limits, disk, temporary workspace
and transfer volume. Record estimates as estimates pending measurements.

Dependencies: framework/version, custom CUDA extensions, CUDA libraries,
generated/traced operators, CPU paths, native MPS coverage and NVIDIA-specific
features. Precision: dtype, accumulation, FP64 requirement, reproducibility and
strict/compatible/fast profile. Costs: initial setup, per-run transfers,
supervision, failed-run recovery and maintenance after environment changes.

The recorded target is MacBookPro18,3/M1 Pro with 16 GiB and its validated
OS/toolchain inventory; do not assume a larger Mac or ignore other memory users.
One large allocation limit is not aggregate capacity, and compression does not
automatically make a model executable within resident memory.

## Route and correctness decision

If the job already works through MPS/native operators, select R-APP evidence
and evaluate its utility honestly. If custom CUDA kernels remain, map each to
the exact compiler/runtime/library prerequisite; tensor backend success does
not eliminate extension compilation or CUDA-only APIs.
NVIDIA-specific operators get an explicit replacement/emulation/unsupported
decision rather than an unexplained generic fallback.

Choose the master contract appropriate to the job: numerical tensors, ML
outputs/gradients/training state, scientific invariants, rendering metrics or
robotics dynamics/control. Freeze independent references and tolerances.
A model-loading or smoke-test success is below application qualification.

## Utility calculation and stop conditions

Measure released RTX capacity using the displaced work actually performed,
not a peak TFLOPS ratio. Report Mac completion time and operator cost alongside
RTX hours saved; do not combine unlike time/cost units into a fake single speedup.
Check the deadline and resource budget after transfer/setup/recovery costs.
Report recurring useful offload separately from one-time demonstration.

Unknown baseline, unavailable input or no valid reference blocks a utility claim,
not all further planning. Defer workloads with unapproved data/model acquisition,
unqualified FP64, missing backend semantics or incompatible resource requirements.
No purchase or reduction of scientific/ML requirements is implicitly authorized.
